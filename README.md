## Start in five minutes — no programming required

1. Open the [current Get Seraphed Community R1 prompt](prompts/GET_SERAPHED_COMMUNITY_R1_LIVING.md) or the simpler [Stage 0 chat-only prompt](prompts/stages/00_CHAT_ONLY_CONTINUITY.md) in an ordinary AI chat.
2. Use a **fictional** project first. Ask for a mission, what is known versus unverified, completed work with evidence, open tasks, failures, and one next safe action.
3. Save the resulting **sanitized handoff card yourself**. In a new chat, verify the current files or evidence again: **nothing transfers permission or authority automatically**. If your AI app remembers earlier chats, run that new chat in a different AI or with cross-chat memory off, so the result reflects only your card.

You can stop here. You do **not** need an AI provider subscription, a local model, access to Seraph, or a running service to use this manual continuity habit. If you later want local software, use the [Stage 1 offline instructions](prompts/stages/01_OFFLINE_CORE.md) and [negative-test checklist](docs/STAGE_1_2_NEGATIVE_TEST_CHECKLIST.md). Keep generated code out of real project folders until its actions and test scope are reviewed.

## Build it in stages

1. [**Stage 0: Chat-only continuity**](prompts/stages/00_CHAT_ONLY_CONTINUITY.md) — useful immediately without installation.
2. [**Stage 1: Offline core**](prompts/stages/01_OFFLINE_CORE.md) — `init`, `status`, `doctor` with real test receipts.
3. [**Stage 2: Task and evidence recovery**](prompts/stages/02_TASKS_EVIDENCE_RECOVERY.md) — task leases, corrected state, failures, backup and restore.
4. [**Stage 3: Memory fidelity**](prompts/stages/03_MEMORY_FIDELITY.md) — source-backed facts, contradictions, corrections and fresh-process reconstruction.
5. [**Stage 4: Optional knowledge and models**](prompts/stages/04_OPTIONAL_KNOWLEDGE_MODELS.md) — rights-aware reference sources and user-approved model adapters; not required for an offline system.

**How is memory actually saved and checked?** Read the new [beginner SHA-256, SQLite event-journal and backup guide](docs/SHA256_MEMORY_INTEGRITY_AND_RECOVERY.md). The records live in actual storage; hash fingerprints help detect inconsistent history, a trusted checkpoint strengthens verification, and a verified backup enables recovery. Neither a hash nor a handoff grants authority or proves factual correctness.

Copy **only one stage at a time** into a chat, verify its real results, save source/test artifacts locally, and resume the next stage with a **sanitized** handoff. In a fresh chat, no old approval carries over. A normal chat may generate useful copyable text without having any access to files or a terminal.

## Why this is different from a simple memory prompt

Most continuity value comes from saving a verified mission and a handoff, but advanced projects benefit from **reproducible negative tests, evidence and failure preservation, history reconciliation, and permissions that do not leak across chats**. A chat summary is not a database; a hash isn't a signature; a model saying PASS isn't a completed test.

**Not verified:** clean-room reproduction of the complete v0.4 build from a fresh AI session, independently audited security, universal long-term memory accuracy, production deployment, or current compatibility with every computer. The historical **30/30** synthetic reference test result belongs to a **different, withheld internal prototype**, not a public executable or a passed public-prompt build. See [verification status](docs/VERIFICATION_STATUS.md) and the [R1 synthetic local-reference report](docs/LOCAL_REFERENCE_R1_HARDENING_20261024.md) (31 developer-authored tests passed on two Macs; executable held, no independent release approval).

**New Stage 1–2 reproducibility trial:** A direct local model built Stage 1 after a syntax repair (**8/8 tests passed**), but its Stage 2 output **failed 5 of 13 independent checks**. A separate **supervised** Stage 2 candidate later passed **57/57 synthetic tests on two Macs**. It is not a fully independent model build and no public executable is released. [Read the evidence and limitations](docs/STAGE2_PUBLIC_PROMPT_TRIAL_20261024.md).

**R3 security follow-up:** Further synthetic testing reproduced three defects in the supervised code—overly broad file permissions, completion before claim time, and failure-ID overflow for long task names. The corrected R3 derivative passed **63/63 first-party tests on two Macs**, with no independent code/security certification or public executable release. See the [R3 report](docs/LOCAL_STAGE2_R3_SECURITY_REVIEW_20261024.md) and [negative-test checklist](docs/STAGE_1_2_NEGATIVE_TEST_CHECKLIST.md). The historical R2 and model-generation failures remain preserved.

**R4 functional follow-up:** A real, verifiable `MISSION.md` and task-bound synthetic evidence now pass **78/78 first-party tests on two Macs**. Fresh direct local coding-model reproductions exposed substantial Stage 1 failures, so full independent Stage 2 reproduction is **not qualified**. [R4 review and its negative receipts](docs/LOCAL_R4_MISSION_EVIDENCE_REVIEW_20261024.md). The executable and private logs remain withheld.

These are scoped local receipts, **not** a security audit, production qualification, software license, or guarantee that another AI can recreate the program.
